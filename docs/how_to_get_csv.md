# 観測地点の外気温データCSVの入手方法
## NOAA: Global Historical Climatology Network (GHCN)

- データ: シアトル（輸出港）と横浜（輸入港）の過去の気温データ。

- 役割: 輸送ルート上の「外気温」のシミュレーション値として使用します。

入手先: [NOAA Climate Data Online](https://www.ncei.noaa.gov/cdo-web/) から City 検索でCSVをダウンロード可能です。

## シアトル・横浜の外気温データ入手手順詳細

### Climate Data Online Search
1. 検索画面へ進む
トップページの青いボックス [Search Tool »] をクリックします。

2. 検索条件を入力する

- 以下の設定で検索をかけます。

  - Select Service: Daily Summaries （日ごとの要約データが扱いやすいため）

  - Select Date Range: ほしい期間を選択（例：2025-01-01 to 2025-12-31）

  - Search For: Stations を選択

  - Enter a Search Term: * シアトルの場合：Seattle、横浜の場合：Yokohama

  - [Search] ボタンをクリックします。

3. 観測地点（Station）を選択する

- 検索結果にリストが出てきます。精度が高いのは空港のデータです。

  - シアトルでおすすめ: SEATTLE TACOMA AIRPORT, WA US

  - 横浜でおすすめ: YOKOHAMA, JA (または近隣の空港)

  - 該当する駅の横にある [Add to Cart] をクリックします。

4. カートの中身を確認し、詳細設定をする

- 右上の [View Cart] をクリックして進みます。

  - Select Cart Output: Custom GHCN-Daily CSV を選択（これがPython等で加工しやすい形式です）。

  - Continue を押すと「Select Data Types」画面になります。

### Select Cart Options

1. Station Detail & Data Flag Options

- 以下の2点に追加でチェックを入れます。

  - [ ] Geographic Location（地理的位置）

    - 理由: 緯度・経度情報が含まれます。複数の観測地点を扱う際、地図上での位置関係を確認したり、将来的に「場所による温度変化」をAIに学習させる場合に役立ちます。

  - [ ] Include Data Flags（データフラグを含める）

    - 理由: 各データに「Q（品質管理済み）」「S（ソース）」などのフラグが付きます。「その値が異常値として弾かれたものか」「欠損値を補完したものか」がわかるため、AI学習データの信頼性（アノテーション）の判断材料になります。

2. Units (単位)

- Standard（華氏 ℉）か Metric（摂氏 ℃）かを選べます。

  - 推奨: 日本での開発や国際標準に合わせるなら Metric に変更しておくと、後のプログラムで (F-32)/1.8 の計算をしなくて済むので楽です。

- Air Temperature の項目にある TAVG (平均気温), TMAX (最高気温), TMIN (最低気温) にチェックを入れます。

### Review Order
1. メールアドレスを入力して注文完了

- 最後にメールアドレスを入力して送信します。数分〜数十分後に、データ作成完了のメールとダウンロードリンクが届きます。

## データの「粒度」は Daily Summaries で充分な理由
今回のプロトタイプ（ONNXモデル）に関しては、まずは Daily Summaries で進めるのが正解です。

理由は以下の3点です。

### 1. データの「粒度」と「目的」の不一致
- Daily Summaries: 1日単位の最高・最低・平均気温。

- Hourly (Local Climatological Data): 1時間ごとの気温。

- 今回の目的: 「コンテナ内の異常（冷却停止など）」を検知すること。

輸送中のコンテナは金属の塊であり、熱慣性が非常に高いです。外気温が1時間で2〜3度変化しても、コンテナ内部の温度は数時間かけてゆっくり追従します。つまり、「その日の大まかな気温」との乖離を見るだけでも、センサー故障や冷却停止は十分に検知可能です。

### 2. 学習データの「マージ」の容易さ

アップロードされた `smart_logistics_dataset.csv` を見ると、ログの記録間隔が不定期（数時間おきなど）です。

- 1時間単位のデータを使う場合: 「`2024-03-20 00:11:14`」というログに対し、「00:00」の気温か「01:00」の気温か、厳密な紐付け（補完処理）が必要になり、前処理スクリプトが複雑化します。

- 日次データ（Daily）の場合: その日の TAVG（平均気温）をバインドするだけで済むため、ノイズに強く、プロトタイプのロジックがシンプルになります。

### 3. APIの制約とデータ量

NOAAのAPIやダウンロードサービスには、一度に取得できる行数に制限があります。

- 1年分のデータを取得する場合、Daily なら`365`行ですが、Hourly だと`8,760`行になります。

- シアトルと横浜の両方を扱う場合、Hourlyだとデータの欠損（Missing Data）が激しくなり、その穴埋め作業だけでエンジニアの工数が削られてしまいます。

### もっと細かいデータが必要になるケース
もし将来的に、以下のような高度な推論を目指すのであれば、Hourly への移行を検討してください。

- 「直射日光による日中の急激な温度上昇」と「深夜の冷却効率」の差までモデル化したい。

- 数分単位で発生する微細な温度変化から、センサーの「予兆検知（劣化）」を行いたい。

### アドバイス
まずは Daily Summaries で 「外気温に対して、明らかに内気温が高い/低い」 という異常検知のパイプライン（Python -> ONNX -> C#）を完成させましょう。

骨組みができてから、「精度が足りない」と感じた時にデータソースを Hourly に差し替えるのが、最も手戻りの少ないアプローチです。
